# Merging product-ui-mode and greenfield-discovery into 2.0

Both branches were written against the 1.x skill, before 2.0 restructured it. A textual merge conflicted in 9 files and would have reintroduced two files 2.0 had replaced, so the merge commits record history only and the content was carried over unit by unit.

**Method.** An inventory workflow split each branch diff into self-contained units (a rule, a table row, a script feature, a lesson), classified each against 2.0 (already covered / merge into a section / new section / new file / conflict / script port / lesson row), and wrote per-file instructions plus a decision for every conflict. One editing agent per destination file applied its instructions; adversarial verifiers then checked, per branch, that every non-skipped unit landed and that no 2.0 rule was lost. `plan.json` holds the units, the per-file instructions, the skipped units with reasons, and the decisions.

**Units:** 416 (product-ui-mode 179, greenfield-discovery 237).

## Decisions

- **product-ui.md (branch) vs app-ui.md (2.0): separate file or fold?** Fold. No product-ui.md in 2.0. Its unique rules go into app-ui.md, which keeps §1–§11 numbered as they are and gains §12 'Brand moments, doors and sign-in', §13 'Traps that show up only while building', §14 'Checklist before implementation (productive surfaces)' and an unnumbered 'Sources read for this reference'. Type for daily use goes into app-ui.md §3, renamed 'Density, type and layout' with its number kept. The Carbon and Material 3 role table goes into design-systems.md §3. Every branch citation of product-ui.md §N is rewritten to the matching app-ui.md or design-systems.md section. *Why:* About half of product-ui.md already exists in app-ui.md (states, tables, notifications, accelerators, a11y baseline). Two productive-UI references with different density numbers would contradict each other. 2.0's vocabulary is posture per route (expressive/productive), not 'application'.
- **The branch a11y.mjs (puppeteer axe matrix) collides with 2.0 a11y.mjs (Playwright, what rule engines miss). Which script?** Do not add the branch file, and leave 2.0 a11y.mjs unchanged. Port its features into the 2.0 harness. audit.mjs gains --themes, --theme-key, the monospace fail with --allow-mono, a non-zero exit on fails, and an axe roll-up by rule. lib/inventory.mjs collects monospace text. lib/env.mjs gains freezeMotion. states.mjs gains --axe, which scans overlays and any stepped state open and generalises the branch's --open chord. Branch documents that name a11y.mjs for axe, themes or mono are re-pointed to audit.mjs or states.mjs --axe. *Why:* In 2.0, axe already runs inside audit.mjs through lib/env.mjs (--storage, settle, dev-server handling). A second puppeteer script would duplicate axe and break the Playwright-only rule. states.mjs steps already reach every open state.
- **Where does the monospace rule live, and what is it numbered?** It becomes a new SKILL.md commitment 5, 'No code fonts unless the audience reads code', and commitments 1–4 keep their numbers. Every branch citation of 'commitment 4' for mono becomes 'commitment 5'. The anti-patterns.md Monospace row drops 'true machine identifiers'. It is allowed only when the product's users read code; otherwise IDs, passwords, env names, [placeholders], key hints and timers use the UI face at 500 with tabular-nums, plus a copy button. A sibling site's mono face is not inherited: this is an explicit exception in audit.md §4 and art-direction.md §4. The browser defaults for code/kbd/samp/pre count. audit.mjs fails on rendered mono unless --allow-mono, which --kind docs implies. *Why:* Code-like type was rejected on three projects (Brandigade, CleoHR, Brio3). A user correction outranks 2.0's allowance, and 2.0's own rule is to put mechanical lessons into a script. 2.0's commitment 4 is 'Measure', so renumbering it would break existing prose.
- **Product density numbers conflict (branch: rows 40–48, compact 32–36, buttons 32–40, titles 24–32; 2.0: controls 28–32, rows 32–40, titles 20–28, and 40–48 px controls is a low-density tell).** Keep 2.0's ranges and name the default inside them. Controls (buttons, inputs): 32 px by default, 28 px compact, 36–40 px only on touch-first surfaces. Table rows: 40 px comfortable (the default), 32 px compact, stacked records on phones. Page titles: 20–28 px, fixed, never fluid; 32 px only for a dashboard or home screen whose single title stands alone. Page header band: 72–120 px. The low-density tell is reworded to '16 px body, controls 40 px or taller and rows 48 px or taller, and 24 px card padding in a desk tool'. *Why:* 2.0's numbers are measured from Twenty, Primer and Carbon, and audit.mjs already uses them. The branch's comfortable row (40) and button range (32) fit at the edge of 2.0's ranges, so nothing measured changes and the branch's comfort intent (a comfortable default) is kept.
- **The greeting: branch brand moment vs 2.0 App-UI tell.** A greeting never takes the page-title slot, which names the place and scope. The display face gets one job: page titles, plus the sign-in screen. The brand-moment budget is 2–3 moments: sign-in, first-run/empty states, and success after a long task. On a home screen a greeting may appear only as a secondary line under a title that names the place. The anti-patterns tell and audit.mjs's greeting check stay. *Why:* audit.mjs already fails a title-slot greeting, and 2.0 learned this from generated dashboards. The branch's real point, a small budget of brand moments, survives without it.
- **Caps in product UI (branch: 1–2 words at 11–12 px, 0.04–0.06 em, column heads and nav group labels; 2.0: 5–12% tracking, one small-caps device per page).** Uppercase only for labels of one or two words in isolation (short column heads, one-word nav-group labels), at 11–12 px, tracked 0.05–0.06 em, in the UI face and never a condensed or hard grotesk. Those labels count together as the page's single caps device. Statuses, multi-word strings and anything scanned down a column stay in sentence case. The type floor is 12 px, with 11 px allowed only for a single uppercase word, and lib/inventory.mjs exempts exactly that case from its 'Text under 12px' warning. *Why:* This keeps NN/g's glanceable-type evidence and 2.0's C1 tracking floor (5%). Counting the label style as one device keeps 2.0's one-device rule intact.
- **Ground colour and accent in all-day apps (branch: warm off-white, accent = action + live state).** The work ground is a low-chroma neutral tinted with the brand hue (design-theory.md B5), not pure #fff and not cream unless the brand owns it. Large saturated fields stay out of the work area. The accent marks action only. Live state is shown with a status colour plus words, and may pulse under the reduced-motion rules. *Why:* 'Warm off-white' reopens the cream/paper house-style cluster that 2.0 gates on the brand. Spectrum's one-colour-for-action principle is already the 2.0 rule.
- **Transition ceiling in product UI (branch ≤ 200 ms vs 2.0 100–250 ms).** Keep motion.md's tokens and app-ui.md's 100–250 ms. Add: nothing animates for attention except live state, and a live-state pulse also states the state in words. *Why:* motion.md tokens (--dur-medium 240 ms) are the canonical values and scripts and templates cite them.
- **Phone navigation (branch: labelled Menu drawer for every app).** Keep the responsive.md §5 table: bottom tabs for 3–5 destinations, and a labelled Menu drawer for many tools or admin. app-ui.md §4 points to it and adds that the phone top bar is the <header> landmark. *Why:* 2.0's table is more specific. The branch rule is its enterprise/admin row.
- **App tables on phones (branch: fold into stacked records; 2.0: numeric tables scroll sideways).** A record list (one row per object) folds on phones into a name plus a meta line, dropping columns the phone does not need. Only a genuine numeric comparison table scrolls sideways, inside the focusable, labelled container with a sticky identifier column. *Why:* This combines both: the branch's folding fixes the common case, and 2.0's container is kept for data that must be compared across columns.
- **Discovery for thin context: file, name and phase number.** Add references/discovery.md titled 'Phase 0 (continued) — Discovery, when the context is thin', keeping the headings '## 1.' to '## 8.' plus '## 5b.' and '## 5c.'. Frame always runs first, and the triage in discovery.md §1 decides whether discovery also runs before Audit. The SKILL.md Phase 0 row is extended rather than duplicated. 'A redesign of a working site starts at Phase 1' becomes 'needs nothing beyond Frame and Audit'. *Why:* 2.0 already calls Phase 0 'Frame' and never skips it. Two Phase 0 rows would contradict the fast path '0 → 1 → …'.
- **Project research folder named research/ (clashes with the skill repo's research/ evidence folder).** In the client project, discovery output goes in discovery/. The write-ups (discovery/brand-audit.md, discovery/domain.md) are committed as project memory. Raw downloads go in discovery/raw/, which is listed in .gitignore and never shipped. Every branch 'research/…' that means the project folder is rewritten this way. 'research/…' keeps meaning the skill repository's evidence. *Why:* This removes the ambiguity and settles what is committed (write-ups) and what is not (raw media).
- **Greenfield: what is 'the old site' for 2.0's old-vs-new checks, and what is the intensity?** The intensity is 'rethink' with no baseline, and the brief says so. What the customer meets today stands in for the old site: the social profile, a competitor's template, a PDF menu. The five first-notice things are taken from that and from the category template. parity.mjs gains --greenfield: no --before, every claim on the new site must appear in --source (discovery/ transcriptions, the owner's answers, content files), and route, id, field and metadata comparisons are skipped and reported as not applicable. The Phase 8 gate accepts that run. *Why:* Without this, a first site either fails 2.0's parity gate or skips it silently. A --source-only claim check keeps the truth commitment mechanical.
- **Signature experiences vs 2.0's posture system (productive novelty 'near zero' would shrink them).** Add a category to framing.md §1 with posture 'signature': 'Signature experience (builder, configurator, studio, visualiser)'. Its fidelity and interaction feel are expressive; its chrome and controls are productive. categories.md gets a playbook and the framing.md §2 switches table gets a note. SKILL.md Phase 0 gets the classification paragraph 'Signature experience or supporting feature?'. It is not a commitment, and the commitments stay at 5. performance.md §1 gets its own budget row. *Why:* The rule was a direct user rejection (the builder shrunk into five form chapters) and needs a home in the classification that drives every later dial.
- **WebGL and smooth-scroll on marketing pages (branch: none; 2.0: purpose-gated).** When a live 3D product exists, the marketing pages around it carry no WebGL: they use stills rendered by the product and hand over to it. Otherwise 2.0's gate stands (a product viewer, a hero object used once). Smooth-scroll libraries are never used on sites that frame a signature product. Elsewhere, 2.0's contained-story allowance stands. *Why:* This scopes the branch rule to the case it was learned on without deleting 2.0's evidence-based product-viewer allowance.
- **Large footer wordmark (2.0 web-design.md §6 calls it 'a legitimate identity moment'; the user called it 'massive branding' and had it removed).** The user wins. Delete the web-design.md §6 sentence. The lockup appears once in the header and once at footer size, and there is no viewport-wide wordmark or mark in the footer or behind the hero. 'Massive branding as a flourish' is added under anti-patterns 'Composition' and named as the skill's own habit. The watermark family in the graphics-layer bullet gets a size limit. *Why:* A direct user correction contradicts a live 2.0 sentence.
- **Header CTA vs hero CTA.** While a hero primary action is on screen, the persistent header CTA is secondary (outline or quiet). web-design.md §6 and responsive.md keep 'the primary action stays visible'. It becomes the primary style only after the hero action has scrolled away, or on pages without one. *Why:* One action colour per view (critique #15) against 2.0's header bullet.
- **Reduced motion: the branch's blanket 0.01 ms block vs 2.0's 'substitute, don't delete'.** Port the lesson, not the snippet. Under reduce, every delay is zero (transition-delay, animation-delay, stagger and delay tokens) while the substitutes keep running. motion.md §4 gains a --delay token set to 0 under reduce. *Why:* A literal port would reintroduce the deleting block that 2.0 replaced.
- **Pause control vs reduced motion (motion.md §2 gate 7 says 'or goes under reduced motion').** Both apply. Anything moving or auto-updating for more than 5 s stops within 5 s or gets a pause control placed before it (WCAG 2.2.2), and reduced motion is respected in addition, never instead. *Why:* WCAG 2.2.2 does not depend on the preference. The branch settles an inconsistency between accessibility.md §2 and motion.md §2.
- **axe gate (2.0 prose: 0 violations; audit.mjs: critical/serious = FAIL, rest = WARN; branch: fix serious/critical, read moderate).** Align the prose with the script. The gate is no audit.mjs FAIL (no critical or serious axe violation), and every moderate or minor violation is fixed or justified in writing. audit.mjs now exits 1 when any page has a Fail. *Why:* SKILL.md's hand-off gate already reads 'no fail you have not fixed or justified'. One wording across technical-qa.md, accessibility.md §12 and the script.
- **Scan coverage: branch 'every route × theme × width, overlays open' vs 2.0 'key templates'; branch script actually scanned less (PX-02).** audit.mjs (automated) runs on every route of a productive surface, taken from parity.mjs --crawl or the route list. With --themes light,dark it runs the full paths × widths × themes matrix, with no dark-only-at-widest economy. Overlays and stepped states are scanned with states.mjs --axe at any device, phone drawer included. a11y.mjs and the manual procedure stay per key template and critical flow. *Why:* The docs must match the tool, and the full matrix is cheap next to a missed dark-mode or phone-drawer failure.
- **Direct manipulation on a canvas: ui-ux.md (branch) or app-ui.md?** ui-ux.md gets a new '## 7b. Direct manipulation on a canvas (editors, configurators, 3D)'. app-ui.md §1 and §8, categories.md, discovery.md §5b and realtime-3d.md point to it. *Why:* Canvases occur on signature, marketing-adjacent and product surfaces alike, and ui-ux.md holds rules every surface obeys. The 7b pattern already exists in 2.0 (app-ui.md §7b).
- **PRODUCT.md vs DESIGN.md brief (principles 5–7 vs 3–5; arrival situations vs top tasks).** Keep templates/PRODUCT.md as the product definition, written before the DESIGN.md brief. PRODUCT.md principles (5–7) are business and product rules ('never show a price the owner hasn't set'). The DESIGN.md brief keeps 3–5 design principles and does not restate them. PRODUCT.md's arrival situations feed the brief's top tasks, and their targets feed its success measures. The document order is PRODUCT.md, then DESIGN.md, then SYSTEM.md. *Why:* The two sets decide different arguments. Stating the relationship prevents them being written twice.
- **realtime-3d.md: separate file or motion.md §9?** Keep references/realtime-3d.md as a file with '## 1.' to '## 9.'. It cites motion.md §9 for the page-level checklist and budgets instead of repeating them. §8 becomes a pointer to motion.md §8–§9 plus the one-canvas warning. It is hooked from SKILL.md's knowledge-base table, motion.md §9 and imagery.md. *Why:* It is a coherent topic 2.0 lacks (building, benchmarking and tuning a real-time 3D product), while motion.md §9 covers 3D on a page.
- **Pushing and permissions for discovery.** Keep 2.0's default of pushing the working branch when the remote is the project's own. Ask once, precisely (what, from where, how much, where stored), before downloading a client's social media, reading their stories, creating accounts, publishing, or pushing a new greenfield repository to a remote. *Why:* This keeps the 2.0 hand-off intact and still covers the actions that notify or commit the client.
- **Accessibility baseline: 'must not regress' (2.0) vs 'must beat' (branch).** The redesign must beat the baseline: every recorded barrier is fixed or justified, and nothing that worked is lost. *Why:* Phase 6 compares against audit/before. Matching a failing baseline ships known barriers.
- **Lesson rows: order and pointers.** Insert rows by date: the two 2026-09-25 Brio3 rows, then the eleven 2026-09-26 and three 2026-09-27 Cake Junction rows, all after the last 2026-09-10 row and before 2.0's first 2026-09-28 row. The six branch 2026-09-28 rows go after 2.0's existing 2026-09-28 rows. Columns 1–4 are kept verbatim. The last column is rewritten to 2.0 locations, with the exact texts given in the lessons.md entry. Digest bullets are added and edited as specified. *Why:* Append, never prune. The 'What changed' column must be true in 2.0.
